# 第1章 概要

> この章の目的
> YoRuu というシステムが何であり、何でないかを明確に定義する。後続全章の前提となる用語・原則・スコープを確定する。

## 1.1 システムの目的

YoRuu は Polymarket の BTC 5分 Up/Down 市場向けの自動売買 Bot である。個人開発者 1名 (本人) が自宅 PC または VPS で運用することを前提とする。商用化・複数ユーザー対応・SaaS 化はスコープ外である。

本プロジェクトの設計インスピレーション元として "Claude × Hermes BTC 5-MIN Polymarket Agent (@Bonereaper)" の画像が存在する。しかし YoRuu はこれを「再現」するものではなく、本質を抽出した自分用の実装である。具体的には、本家のもつ Markov + Kelly による数式判定・夜間レビューによる自己学習ループという核心は継承しつつ、外殻 (Telegram, Hermes Agent, 完全自動の LLM 連携) は安全性・コスト・シンプルさの観点で意図的に置き換える。

YoRuu は娯楽用ではなく実資金を扱う性質を持つ。したがって設計のあらゆる場面で、機能性より安全性が優先される。

## 1.2 本家との差分

| 項目 | Bonereaper (オリジナル) | YoRuu (本実装) | 差分の理由 |
|---|---|---|---|
| 取引判定 | Markov + Kelly (LLM不使用) | 同じ | 数式判定の本質を継承 |
| 夜間レビュー実行 | Claude Opus 4.7 が自動実行 | 人間が Genspark 経由で Opus 4.7 に手動依頼 | コストゼロ + LLM の暴走防止 |
| 通知 | Telegram Bot | ローカルログ + Web UI バナー（SSE）のみ | 依存削減・操作の一元化 |
| エージェント基盤 | Hermes Agent (NousResearch) | なし、Python 単体 | 不要な複雑性の排除 |
| インフラ | Hetzner VPS | Hetzner VPS またはローカル PC | 開発・運用の柔軟性 |
| 動作モード | live のみ | backtest / paper / simmer / live の4モード | テスト可能性の確保 |
| パラメータ適用 | 完全自動 | 検証 + 二重承認を経て適用 | 暴走防止 |
| ソースの公開状態 | 完全クローズド | 個人 private リポジトリ | 個人開発・自己責任 |

## 1.3 想定ユーザー

YoRuu の利用者は本人 1名のみである。前提とする知識レベルは以下のとおり。

- Python の基本的な読み書きが可能である
- Cursor などの AI 補助 IDE を運用できる
- Cron / systemd の基本概念を理解している
- 基本的な SQL を読める
- 投資判断は自己責任で行える成人である

複数ユーザー対応・ログイン認証・課金等の機能は持たない。Web UI は localhost (またはユーザー本人がアクセスできる VPS) に閉じる前提で設計される。

## 1.4 設計原則

YoRuu はトレードオフが発生したとき、以下の5原則に従って判断する。原則は上から優先順位が高い。

| # | 原則 | 反する例 | 従う例 |
|---|---|---|---|
| 1 | シンプルさ最優先 | 「将来のために」と未使用機能を入れる | 必要になるまで実装しない |
| 2 | 安全性は機能性に優先する | live モードでの即時実行を優先しスキーマ検証を省略 | 検証なしで進む経路を構造的に作らない |
| 3 | テスト可能性 | live モードでしか動かないコードがある | 全機能が paper / backtest で再現できる |
| 4 | 低コスト運用 | 高頻度ポーリングで API レート制限を消費する | WebSocket + キャッシュで最小限のコールに抑える |
| 5 | 可観測性 | エラー時に何が起きたかログに残らない | 全状態遷移・全 API 呼び出しが構造化ログに残る |

## 1.5 スコープ

### スコープ内

- Polymarket の BTC 5分 Up/Down 市場での自動売買
- Markov 連鎖による状態推定と Kelly 基準によるサイズ決定
- 4つの動作モード (backtest / paper / simmer / live)
- ローカル Web UI による操作・監視
- 夜間レビュー機構 (Opus 4.7 への手動連携を介した戦略パラメータ更新)
- 戦略パラメータの検証付き書き換え機構
- 監査ログ・キル・スイッチ・二重承認等の安全機構
- SQLite による永続化
- ローカル PC または単一 VPS での運用

### スコープ外

明示的に「やらない」と決めるもの:

- ETH / SOL / XRP など他資産の取引
- 15分・1時間など他の時間枠の市場
- 複数ユーザー対応・ログイン認証・権限管理
- モバイルアプリ・ネイティブクライアント
- スマートコントラクトの独自実装
- 機械学習モデルの自前訓練 (LLM 呼び出しに依存)
- 高頻度取引 (HFT) のためのレイテンシ最適化
- 完全自動の夜間レビュー (将来検討事項)
- 通知 (Telegram / メール / Slack 等)
- Polymarket 以外のプラットフォーム対応

## 1.6 用語集

本設計書全体で使用する用語の定義である。後続章はこの用語を厳密に使用する。

| 用語 | 英 | 定義 |
|---|---|---|
| Markov連鎖 | Markov chain | 直近状態のみから次状態の確率を推定する確率モデル |
| 持続状態 | persistent state | 上昇または下降が連続している状態 |
| Persistence | persistence | Markov 推定の遷移確率（例: p(UP→UP)）。分析・表示用 |
| Kelly基準 | Kelly criterion | f* = p - (1-p)/b で最適賭け金比率を求める公式 |
| エッジ | edge | モデル推定確率 p とマーケット価格 q の差 (p - q) |
| CLOB | Central Limit Order Book | 中央集権型指値注文板。Polymarket の取引方式 |
| EIP-712 | EIP-712 | Ethereum の構造化データ署名規格。Polymarket 注文に必須 |
| ペーパーモード | paper mode | 実取引せず、リアルタイム市場で仮想約定するモード |
| Simmer | Simmer | Polymarket 向けペーパートレード提供サービス |
| backtest モード | backtest mode | 過去データで戦略を高速再生するモード |
| live モード | live mode | 実資金を投入する本番モード |
| persistence_threshold | persistence threshold | 直近 N 本の同方向継続割合の最小値（エントリー許可）。`MIN_PROB` とは別尺度 (→ 第12章) |
| MIN_PROB | MIN_PROB | エントリー方向の最小モデル確率（Kelly 入力の p） |
| MIN_EDGE | MIN_EDGE | エントリーを許可する最小エッジ |
| KELLY_FRACTION | KELLY_FRACTION | Kelly 基準の数値を実際にどれだけ使うかの係数 (0〜1) |
| 不変条件 | invariant | 常に成立しなければならない条件 |
| キル・スイッチ | kill switch | 緊急停止機構 |
| 二重承認 | two-step confirmation | 危険操作で2段階の確認を要求する仕組み |
| 戦略パラメータ | strategy parameters | strategy.json で管理される動的パラメータ群 |
| 夜間レビュー | nightly review | 1日1回の戦略パラメータ見直しプロセス |
| Apply | apply | 新戦略パラメータを strategy.json に書き込む操作 |
| 監査ログ | audit log | 改ざんできない形で全変更を記録するログ |
| Zone | zone | 信頼境界線で区切られた領域 (Zone 0〜3) |
