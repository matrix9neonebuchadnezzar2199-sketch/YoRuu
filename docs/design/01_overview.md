# 第1章 概要

## この章の目的

YoRuu のシステム目的、本家との差分、想定ユーザー、設計原則、スコープ、用語集、および全24章のドキュメント構成を定義する。後続章の用語・前提の基準となる。

---

## 1.1 システムの目的

YoRuu は **Polymarket** の **BTC 5分 Up/Down** 市場向け自動売買 Bot である。

- **運用形態**: 個人開発者 1 名が自宅 PC または Hetzner VPS で常時稼働
- **判定方式**: Markov 2状態遷移 + Kelly 基準（**ランタイム LLM 不使用**）
- **進化方式**: 1日1回の **夜間レビュー** で戦略パラメータを人間監督のもと更新

設計のインスピレーションは "Claude × Hermes BTC 5-MIN Polymarket Agent (@Bonereaper)" であるが、YoRuu は画像の **再現** ではなく、Markov + Kelly・低コスト運用・人間レビューという **本質を抽出した自分用実装** である。

商用化・マルチユーザー・SaaS 化は **スコープ外** とする。

## 1.2 本家との差分

| 項目 | Bonereaper (オリジナル) | YoRuu (本実装) | 差分の理由 |
|:---|:---|:---|:---|
| 取引判定 | Markov + Kelly (LLM不使用) | 同じ | — |
| 夜間レビュー実行 | Claude Opus 4.7 が自動実行 | 人間が Genspark 経由で Opus 4.7 に手動依頼 | コストゼロ + 安全性向上 |
| 通知 | Telegram Bot | なし、すべて Web UI で完結 | シンプル化 |
| エージェント基盤 | Hermes Agent (NousResearch) | なし、Python 単体 | 不要な複雑性の排除 |
| インフラ | Hetzner VPS | Hetzner VPS または ローカル PC | 柔軟性 |
| モード | live のみ | backtest / paper / simmer / live の4モード | テスト可能性 |
| パラメータ適用 | 完全自動 | 検証 + 二重承認を経て適用 | 暴走防止 |

## 1.4 設計原則

### 1. シンプルさ最優先

機能追加より既存機能の堅牢化を優先する。

- **反する例**: Telegram・Hermes・複数 LLM パイプラインを同時に導入する
- **従う例**: Web UI + ローカル JSON + 単一 `yoruu.yaml` に集約する

### 2. 安全性は機能性に優先する

動かないより、誤動作する方がはるかに危険である。

- **反する例**: Opus 返却 JSON を検証なしで `strategy.json` に上書きする
- **従う例**: スキーマ検証・範囲検証・二重承認・バックアップ後に適用する

### 3. テスト可能性

ライブモードに行く前に検証できないものは作らない。

- **反する例**: 未検証の戦略をいきなり live で稼働させる
- **従う例**: backtest → paper → simmer → live の段階的昇格を強制する

### 4. 低コスト運用

月額固定費は VPS 約 $6/月のみを目標とする。

- **反する例**: ランタイムで有料 LLM API を毎5分呼び出す
- **従う例**: 取引判定は純 Python 数式、夜間レビューのみ既存 Genspark 契約を利用する

### 5. 可観測性

何が起きたか後から完全に追える状態を維持する。

- **反する例**: 戦略変更理由をログに残さない
- **従う例**: 監査ログ・戦略履歴・構造化ログ・日次レポート JSON を永続化する

---

## 1.5 スコープ

### スコープ内

- BTC 5分 Up/Down 市場での自動売買
- Markov + Kelly 戦略
- 4モード（backtest / paper / simmer / live）
- Web UI による操作・監視
- 夜間レビュー機構（Opus 4.7 への手動連携）
- 戦略パラメータの安全な書き換え
- 監査ログ・キル・スイッチ

### スコープ外（明示的にやらない）

- ETH / SOL / XRP など他資産
- 15分・1時間など他の時間枠
- 複数ユーザー対応・ログイン認証
- モバイルアプリ
- スマートコントラクト独自実装
- 機械学習モデルの自前訓練
- 高頻度取引（HFT）最適化
- 完全自動の夜間レビュー（Phase 2 以降の検討事項）

## 1.6 用語集

本設計書全体で以下の表記を用いる。英語併記は初出または識別子として使用する。

| 用語 | 英 | 定義 |
|:---|:---|:---|
| Markov連鎖 | Markov chain | 直近状態のみから次状態の確率を推定する確率モデル |
| 持続状態 | Persistent state | 上昇または下降が連続している状態 |
| Persistence | — | 同一方向が連続する確率（例: UP→UP の確率） |
| Kelly基準 | Kelly criterion | \(f^* = p - (1-p)/b\) で最適賭け金比率を求める公式 |
| エッジ | Edge | モデル推定確率 \(p\) とマーケット価格 \(q\) の差 \((p - q)\) |
| CLOB | Central Limit Order Book | 中央集権型指値注文板。Polymarket の取引方式 |
| EIP-712 | — | Ethereum の構造化データ署名規格。Polymarket 注文に必須 |
| ペーパーモード | Paper mode | 実取引せず、リアルタイム市場で仮想約定するモード |
| Simmer | — | Polymarket 向けペーパートレード提供サービス |
| persistence_threshold | — | エントリーを許可する最小 Persistence |
| MIN_PROB | — | エントリーを許可する最小モデル確率 |
| MIN_EDGE | — | エントリーを許可する最小エッジ |
| KELLY_FRACTION | — | Kelly 基準の数値を実際にどれだけ使うかの係数（0〜1） |
| 不変条件 | Invariant | 常に成立しなければならない条件 |
| キル・スイッチ | Kill switch | 緊急停止機構 |
| 戦略パラメータ | strategy parameters | `strategy.json` に格納される閾値群 |

**表記ルール**: 本文では「Bot」「ユーザー」「ペーパーモード」「ライブモード」「夜間レビュー」を用い、「ボット」「ユーザ」等は使用しない。
